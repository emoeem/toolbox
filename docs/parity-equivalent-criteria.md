# ImageToolbox → Toolbox `equivalent` 判定标准

## 目的

`equivalent` 不是“能运行”或“看起来类似”。只有当同一 ImageToolbox feature 的可见功能、参数、输出、边界和主要交互路径均有证据通过时，才允许升级。

## 五项硬条件

| 条件 | 判定要求 | 量化方式 |
|---|---|---|
| 功能点覆盖 | ImageToolbox 用户可见功能点逐项有对应实现 | 建立 feature → function/UI action 清单；任何缺失项直接不通过 |
| 参数覆盖 | 每个用户可见参数可设置，并且改变参数确实影响行为 | 至少两个有效参数集；输出尺寸、统计量、SHA 或像素差至少一种发生可解释变化；离散枚举逐项覆盖 |
| 输出一致 | 相同输入/参数下，输出语义与关键特征一致 | 图像：尺寸、通道、像素统计、固定输入下 SHA/差异图；文本/元数据：字段和值逐项比较；允许 Android/desktop 编码差异时必须注明容差 |
| 边界一致 | 空、最小、最大、越界、非法格式等行为与参考实现语义一致 | 明确记录“拒绝/回退/成功”的参考行为；不能只证明“不崩” |
| 交互一致 | 用户可完成相同主要操作路径 | 记录入口、参数面板、执行、取消/保存/导出等关键动作；无法在当前平台复现的部分保持未验证 |

## 无法直接量化时

必须把比较对象转成可观察证据。例如：

- Android GPU 输出无法逐字节等同：比较尺寸、颜色统计、边缘/结构特征，并以固定输入运行两组参数。
- UI 行为无法用 SHA 表示：记录动作序列、状态变化、可见控件和最终输出。
- 后端依赖不同：比较最终语义结果，同时记录 backend 与版本，不把不同 backend 的实现差异隐瞒为一致。

## 升级规则

- 五项全部通过 → `equivalent`
- 任意一项缺失、失败或未验证 → 保持当前等级
- “代码存在”“可以执行”“输出非空”最多支持 `runnable/usable`，不能单独支持 `equivalent`
- 不允许用平均分或部分覆盖抵消缺失项
